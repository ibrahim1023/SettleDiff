# Evidence transparency: Phase 2 design

**Design only, 2026-10-15. No log or witness is implemented or selected.** The
owner confirmed there is no committed external history verifier. The recommendation
in [proposed ADR 0016](../decisions/0016-defer-evidence-transparency.md) is to defer
implementation. This document describes the conditions under which it would help.

## The question a consumer would need to ask

Individual signed bundles already answer: “Did my trusted issuer sign these exact
artifacts?” History transparency would address a different question: “Is this signed
issuance included in the same extending history that my organization previously
accepted?” A possible consumer is an auditor comparing report deliveries across
review periods. That is an example, not an existing customer or requirement.

A successful inclusion proof would still say nothing about reports never submitted.
A policy requiring every issuance to enter a log would need its own enforceable
issuance/acknowledgement contract and monitoring. It cannot be inferred from SQLite
run counts, payment counts, or a collection of proofs supplied by the issuer.

The current code keeps immutable report records and local append-only timeline
observations, while `SQLiteReportRepository.delete` permits per-run deletion.
These are local retention semantics, not public non-equivocation guarantees. The
existing public projection and Logfire integration do not provide checkpoint
witnessing. No existing report, local timeline, or telemetry record changes here.

## Candidate separation of roles

| Role | Responsibility | Does not establish |
|---|---|---|
| Issuer | Sign the private bundle under the recipient's trusted issuer key | Truth or neutrality of the evidence |
| Log | Order opaque commitments, produce roots/proofs, and sign checkpoints | Settlement or complete issuance |
| Witness | Retain state and cosign only compatible checkpoint extensions | Meaning of private evidence |
| Monitor | Independently collect checkpoints, compare views, and investigate exceptions | Knowledge of deliberately unsubmitted reports |
| Recipient | Verify issuer authentication, opening, history proofs, and its pinned trust policy | A newest global view while offline |

Require different key roles. Separating key files without separating administrators,
state, and compromise domains does not provide organizational independence. A monitor
can examine private openings only through an authorized disclosure channel; a public
monitor otherwise sees opaque entries and checkpoint behavior.

A future consumer must first choose whether checkpoint/entry access is restricted
to an auditor group or publicly accessible. External retention does not require
posting evidence to the public Internet. Public access is not the default choice;
the disclosure rules below also protect data shared with an external log operator.

## Candidate private-to-public binding

Keep bundle schema 3 and `assurance-signature/v1` untouched. After export/signing,
a separately authorized publication step could create a private history receipt.
The candidate commitment is:

```text
C = SHA256("SettleDiff private assurance log commitment v1\0"
           || random_private_32_bytes
           || SHA256(exact_issuer_envelope_bytes))
```

The fixed domain string is ASCII including its terminal NUL; the remaining inputs
are fixed 32-byte strings. The public leaf content is only `C`. The nonce is fresh
for each issuance, generated by an OS cryptographic random source, retained privately,
and never posted or put in telemetry. The exact saved envelope bytes are bound;
rewrapping its JSON can preserve Phase 1 authentication but would require the
original bytes to open this particular commitment. This is a candidate encoding,
not an adopted artifact format or a new assurance claim.

A private presentation would contain the existing bundle and issuer envelope,
private nonce, leaf index, inclusion path, authenticated checkpoint and witness
cosignatures, and any consistency proof required by the recipient's retained
baseline. Loss of the nonce prevents opening that entry. Disclosure of an opening
makes the corresponding entry linkable; recipients must understand onward sharing.

Public output must exclude all financial fields, URLs from evidence, wallet and
transaction IDs, run IDs, wallet/payment signatures, seller JWS, private issuer
signatures or issuer-envelope bytes, private bundle/
manifest hashes, and nonce openings. Opaque commitments still expose ordering,
volume, and timing; protocol-specific signer linkage and submission IP metadata
also need review. Batching may reduce timing precision but is not anonymity.
Local deletion cannot retract a public commitment. No publication is authorized
by this design, including synthetic submissions to an operating public log.
The selected protocol's public log/witness keys and checkpoint signatures are a
separate allowlist: they must be disclosed to authenticate checkpoints, after the
privacy contract is approved. This exception never includes private issuer-envelope
signatures, seller JWS, or reusable payment signatures. A backend requiring banned
private fields is ineligible without a separately approved disclosure change.

## Tree, checkpoints, and external state

Use a maintained implementation of the domain-separated Merkle construction and
proof verification described in [RFC 9162 §2.1](https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1),
not custom elliptic-curve code or a home-made hash chain. Empty and non-power-of-two
trees must follow the selected protocol's exact rules. Inclusion binds an entry to
a root; consistency connects an older authenticated root to a later one.

A candidate checkpoint follows the published
[C2SP checkpoint format v1.1.0](https://c2sp.org/tlog-checkpoint@v1.1.0): origin,
size, root, and signed-note signatures. Exclude optional extension lines from the
SettleDiff profile. Pin the supported signature variants and their exact framing;
issuer-envelope JSON is not checkpoint-note encoding. Current C2SP guidance includes
ML-DSA-44 cosignatures, so complete receipt size cannot be estimated from Ed25519's
64-byte signature alone. No new cryptographic algorithm is adopted here.

The [witness protocol](https://c2sp.org/tlog-witness@v1.1.0) verifies consistency
against retained state and requires atomic persistence before acknowledging a
checkpoint. A future operator contract must cover state loss, concurrent requests,
backup restoration, and key compromise. A signature over an arbitrary new root is
not a substitute for that stateful check.

The recipient independently pins the log origin/key and witness policy. It retains
its last accepted checkpoint outside the issuer's control. First-use bootstrap must
come from a separately authenticated checkpoint or explicitly accept that earlier
history has not been checked. A new log identity/epoch must not silently erase this
baseline. Recovered witnesses must not simply bootstrap from size zero after losing
state; operators must restore and reconcile trusted state before resuming.

At least one independent required witness is a minimum design constraint, not an
unconditional security guarantee. If future clients use threshold witness sets,
prove that any accepted pair overlaps in an honest witness for the stated collusion
bound. For a uniform pool of `N` witnesses, threshold `q`, and at most `f` dishonest
members, the sufficient intersection condition is `2q > N + f`; this alone does
not establish independence, freshness, or availability. Arbitrary “two signatures”
and keys controlled by one administrator are insufficient.

Publish checkpoints through an agreed external channel and have a responsible
monitor retain/compare them, including witness-side views where supported. The
issuer's own rewritable Git repository is not the independent state holder.
Checkpoint age and clock-skew limits need consumer agreement. A valid old proof
must not be represented as proof of current global freshness.

## Verification and failure behavior

A future recipient verifies Phase 1 issuer authentication first, recomputes the
private commitment, authenticates the checkpoint's origin/key and required witness
policy, validates inclusion at its declared index/size, and connects that checkpoint
to its own trusted baseline. Only then may its retained baseline advance atomically.
Trusted keys/policy must never be supplied solely by the receipt being checked.

| Situation | History interpretation | Financial result |
|---|---|---|
| Valid issuer bundle; no history receipt | Issuance authenticated; shared history unavailable | Original verdict |
| Log inclusion; issuer authentication fails | No trusted SettleDiff issuance established | No new verdict |
| Missing/invalid proof or witness outage | New history claim cannot be accepted | Original verdict |
| Signed checkpoints with same origin/size and different roots | Evidence of conflicting log views; preserve both and investigate | Original verdict |
| Lower size or stale checkpoint | Reject state rollback or freshness claim under the chosen policy | Original verdict |
| Private evidence deleted, commitment remains | Historical commitment may remain; evidence availability is separate | No fabricated replacement report |

A missing consistency proof can reflect an outage; it does not alone prove
malicious equivocation. Never retry a payment to repair a log failure, alter
settlement observation, or reinterpret `AUTHENTIC` as a transaction verdict.
History outcomes would be a separate detached result, requiring a later accepted
contract. No history-related status is added to existing models by this design.

## Calculated benefit and benchmark limits

For SHA-256, let `h = ceil(log2(n))`. An inclusion path has at most `h` sibling
hashes; the RFC's consistency bound is `h + 1`. Each hash is 32 bytes. These
calculations were executed with the locked Python environment on 2026-10-15:

| Entries `n` | All leaf digests, bytes | Inclusion hashes, at most bytes | Consistency hashes, at most bytes |
|---:|---:|---:|---:|
| 1,000 | 32,000 | 320 | 352 |
| 1,000,000 | 32,000,000 | 640 | 672 |
| 1,000,000,000 | 32,000,000,000 | 960 | 992 |

The compared list is only a digest list, not full evidence. Proof columns exclude
checkpoints, cosignatures, keys, framing, leaf payload, and private opening. Paths
may be shorter. This is a size/complexity estimate, **not a runtime benchmark**.
A reproducible calculation, without implementing any tree or proof code:

```bash
uv run --offline python - <<'PY'
from math import ceil, log2
for n in (1000, 1000000, 1000000000):
    h = ceil(log2(n))
    print(n, 32 * n, 32 * h, 32 * (h + 1))
PY
```

For a recipient tracking many entries, compact paths can avoid downloading a
complete history for each membership check. For today's consumer verifying one
bundle, this adds proofs, keys, external trust, storage, and latency; it does not
remove hashing the bundle or checking its issuer signature. No measured client
speedup, witness latency, hosting bill, or throughput is claimed.

Before implementation approval, the consumer must set budgets and authorize a
synthetic-only comparison against Phase 1: actual receipt bytes by signature mode,
p50/p95 verification and publication latency, append throughput, CPU/peak memory,
index growth, checkpoint retention, witness traffic, and outage recovery. Pin the
backend, version, license, hardware, dataset seed, and command before measurement.
No backend or benchmark implementation is selected here.

## Future acceptance matrix and go/no-go

Any later implementation needs independent known-good vectors and negative cases
for empty/one-leaf/odd trees, tree-boundary sizes, changed entries and leaf indices,
extra/truncated/reordered proofs, wrong roots/origins/keys, incompatible checkpoints,
rollback, unknown/duplicate witnesses, disjoint threshold sets, stale timestamps,
state races/restoration, issuer substitution, nonce reuse/loss, and disclosure leaks.
It also needs backward-compatibility and no-payment/no-network default-test gates.
These are proposed acceptance criteria, not tests that have run.

**No-go today:** the owner has no committed external history verifier; there is
no agreed witness/monitor arrangement, disclosure contract, or performance budget.
The reopening requirements are in ADR 0016. Phase 2 delivers this design and source
research only. There is no public log, witness deployment, TLSNotary integration,
or ZK implementation, and none is needed for current signed-bundle verification.

## Design review and verification

Primary-source review checked the tree/proof claims, witness state and quorum
assumptions, offline freshness limits, and calculated-size wording. It identified
one disclosure ambiguity: private signature material must remain excluded, while
approved log/witness checkpoint authentication metadata must be shareable. The
allowlists above distinguish those roles.

The size calculation printed the three rows above. `uv lock --check`, Ruff format
and lint checks, Pyright, `uv run python scripts/check_docs.py`, and `git diff --check`
passed for this documentation change. No new runtime tests were added or run:
there is no implementation to test. The future acceptance matrix is not a claim
of executed coverage, a security audit, or measured runtime performance.
